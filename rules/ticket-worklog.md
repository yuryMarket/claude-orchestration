# Worklog закрытия задачи

## Назначение

Каждая задача с тикетом (Jira `COR1-*` или любой другой) при закрытии завершается **worklog'ом** — историей выполнения от имени пользователя как SRE-инженера, опубликованной комментарием в Jira. Пользователь проводит по нему демо: что и как было сделано.

Правило действует в **обоих режимах**: прямая сессия и AIDD.

Утверждённые образцы:
- worklog: `COR1-581` → `docs/reports/COR1-581-worklog.md` (проект core-ai), комментарий Jira id `4314208`;
- полный формат закрытия (описание + worklog на B1 + резюме): `COR1-637` — worklog комментарий `4449724`, резюме комментарий `4497131`; описание — также эталон `COR1-610`.

## Когда срабатывает

Момент закрытия задачи:
- Ответ разработчику отправлен.
- PR смержен.
- Тикет переводится в Ready for Demo (см. «Статус тикета при закрытии»).
- Пользователь говорит «задача закрыта».

Также по явному вызову `/worklog <ticket>` — в том числе постфактум для уже закрытых задач: тогда путь реконструируется из транскриптов и артефактов.

| Режим | Где описан шаг |
|---|---|
| Механика выполнения | `~/.claude/skills/worklog/SKILL.md` |
| AIDD | Этап 9 в `~/.claude/workflow.md` |
| Прямая сессия | Шаг «Закрытие задачи» в `routing.md` |

## Порядок закрытия

Строго по шагам:

1. Описание тикета актуализировано по `ticket-description.md`.
2. Worklog опубликован.
3. Комментарий-резюме опубликован — самым последним комментарием.
4. Перевод в Ready for Demo.

## Статус тикета при закрытии

Закрытие тикета в **обоих режимах** (прямая сессия и AIDD) означает перевод в статус **Ready for Demo** — в Jira THD так называется колонка «Demo». Это подразумевается всегда: и когда Claude закрывает тикет сам по завершении работы, и когда пользователь говорит «закрой тикет» / «задача закрыта» / «переведи в закрытые».

- **Никогда** не переводить тикет в `Done` (и любой другой финальный статус). В `Done` тикет переводит пользователь сам после демо.
- Перевод статуса — только через агента `general-purpose`: `mcp__atlassian__jira_get_transitions` → `mcp__atlassian__jira_transition_issue` на transition «Ready for Demo». Оркестратор `mcp__*` не вызывает — см. `mcp-isolation.md`.
- Порядок строго по секции «Порядок закрытия». Перед сменой статуса убедиться, что worklog и комментарий-резюме уже в тикете.
- Если transition «Ready for Demo» недоступен из текущего статуса — замену не подбирать: сообщить пользователю список доступных transitions и **СТОП**.

## Голос и язык

- Первое лицо, от имени пользователя, как писал бы человек-SRE.
- **Никаких упоминаний** Claude / ИИ / агентов / сессий / транскриптов.
- Язык worklog — язык тикета и аудитории демо (для THD Jira — английский).
- Уровень английского — простой B1, максимум B2: короткие предложения, простая лексика, технические термины и идентификаторы как есть. Структура worklog от этого не меняется.
- Общение с пользователем в чате — русский.

## Сбор фактов перед написанием

Ничего не выдумывать. Источники:

| Источник | Как получить |
|---|---|
| Тикет: комментарии, история | агент `quick-lookup` |
| Транскрипты сессий | `~/.claude/projects/<проект>/*.jsonl` — grep по ID тикета, именам ресурсов, имени автора запроса |
| Локальные артефакты | `docs/`, `~/docs/quick-lookup/`, `~/infra-operator-logs/` |
| GitHub | `gh pr view`, `gh api .../contents/...` — проверка существования файла и получение `html_url` |
| Состояние систем | read-only проверки `bq` / `gcloud` / `kubectl` при необходимости |

Тупики и ошибочные ветки описывать **только реальные**.

## Структура тела комментария

Комментарий **без заголовка** — никакого `## ...` в начале. Тело состоит строго из двух блоков по порядку: сначала краткое резюме результата, затем **маркированный список** шагов (bullet, **НЕ нумерованный**: Jira Markdown→ADF рендерит многострочные нумерованные пункты как 1, 1, 1).

### Блок 1 — краткое резюме результата

Идёт первым — с первой строки комментария, до пошагового списка.

- Очень краткое: несколько строк, не абзац-полотно.
- Фактическое и структурированное: что удалено / добавлено / исправлено / изменено и к чему это привело. Формулировка вида «Removed X, added Y, fixed Z. As a result <что изменилось / что теперь работает>» — на языке тикета (для THD Jira — английский).
- Это резюме **результата**, а не пересказ пути: путь описывается ниже, в пошаговом списке.
- Без внутренних заголовков, рубрик и bold-подписей — это не рубрикатор, а несколько фактических строк.
- Без оценок собственной работы и ремарок о её важности («critical fix», «major improvement»).

### Блок 2 — пошаговый список

Каждый пункт — один абзац, один шаг истории, хронологически:

1. Какой контекст уже был (предыдущие тикеты / PR, благодаря которым ответ нашёлся) — без вводного «вопрос пришёл от X в канале Y такого-то числа», это видно из тикета.
2. Куда пошёл сначала, что там узнал.
3. Куда пошёл потом — включая ошибочные ветки, явно: «это был не тот путь, потому что…».
4. Что сделал руками: PR, правки, деплой, проверки.
5. Что и где ответил разработчику — краткая суть ответа внутри пункта.
6. Хозяйственные действия по тикету (оформление описания, смена статуса).

**Каждый пункт заканчивается фразой `Resources and result:`** и ссылками именно этого шага; у каждой ссылки короткая подпись (что показывает): файл в GitHub (`blob/main/...`), PR, консоль GCP, Slack-канал / тред, тикет, дашборд, лог.

## Комментарий-резюме

После worklog публикуется **отдельный** комментарий — он должен быть **самым последним** в тикете. Worklog остаётся; резюме его не заменяет и не пересказывает путь. В описание тикета резюме не добавляется.

- Первая строка — ровно `Summary of work done:`.
- Затем нумерованный список. Здесь нумерация разрешена и обязательна: каждый пункт — **одна строка** (многострочные пункты Jira рендерит как 1, 1, 1).
- Каждый пункт — конкретное практическое действие со ссылкой и кратким пояснением, что оно дало: `[PR #N](url): что сделано`, сборка образа, деплой, созданный endpoint, проведённый тест или проверка.
- Язык — английский B1, максимум B2; без оценок и упоминаний Claude / ИИ.
- Существующее резюме искать по фразе `Summary of work done:`. Правки — `jira_edit_comment` того же комментария, не новым.

Мини-шаблон:

```
Summary of work done:

1. [PR #N](url): <what was changed>.
2. Built image `<name>:<tag>` in [<registry>](url): <what it gives>.
3. Deployed to <env> via [Spinnaker](url): <what works now>.
4. Ran <test / check> ([log](url)): <result>.
```

## Приведение существующего тикета к формату

По запросу пользователя «переделай задачу в формат»:

1. Бэкап: исходное описание и все комментарии — в `docs/reports/<ticket>-description-original.md`.
2. Черновики:
   - описание — по `ticket-description.md`;
   - worklog на B1: если worklog уже есть (фраза `Resources and result:`) — переписать тот же комментарий; если нет — написать по алгоритму этого правила;
   - комментарий-резюме по секции «Комментарий-резюме».
3. Показать черновики пользователю → **СТОП**.
4. После подтверждения — применить через агента `general-purpose`: описание (и заголовок) — Rovo `mcp__claude_ai_Atlassian_Rovo__editJiraIssue` в формате markdown (не `jira_update_issue`, см. `ticket-description.md`), `jira_edit_comment` или `jira_add_comment` (worklog), резюме последним комментарием.
5. Обратное чтение тикета: описание — через Rovo `mcp__claude_ai_Atlassian_Rovo__getJiraIssue`; описание, списки и ссылки отрендерились, резюме — последний комментарий.

Ограничения:
- Статус тикета при этом не менять.
- Чужие комментарии (не worklog пользователя) не редактировать.

## Чего НЕ должно быть

Отвергнуто пользователем явно:

- Отдельных секций Request source / Question / Context / Investigation path / Answer / Work beyond research / Result / Demo links / Follow-ups.
- Вводной фразы про источник запроса.
- Абстрактных рассуждений «как бы я шёл без контекста».
- Нумерованных списков в worklog. В комментарии-резюме, наоборот, нумерованный список однострочных пунктов обязателен.
- Любых markdown-заголовков в теле worklog, включая `## Work log — how this request was handled`: отвергнут явно (2026-09-24, COR1-591). Комментарий начинается сразу с резюме результата.

Краткое резюме в начале — **не** возврат к этим секциям: оно одно, без заголовков и рубрик внутри, и не заменяет пошаговый список.

## Ссылки

- Перед публикацией проверять, что файл / PR существует и URL корректен.
- Избегать URL со спецсимволами `!` и подобными: deep-link консоли BigQuery вида `ws=!1m5!...` ломается при Markdown→ADF. Давать простой URL консоли с `?project=`.

## Хранение и публикация

1. Файл: `docs/reports/<ticket>-worklog.md` в проекте (режим 1 из `docs-storage.md`) или `~/docs/reports/` вне проекта.
2. Показать черновик пользователю → **СТОП**.
3. После подтверждения — опубликовать комментарием в Jira через агента `general-purpose` (`mcp__atlassian__jira_add_comment`), Markdown как есть: тул сам конвертирует в ADF. Оркестратор `mcp__*` не вызывает — см. `mcp-isolation.md`.
4. После публикации — обратное чтение комментария: проверить, что список и ссылки отрендерились.

Уже опубликованный worklog-комментарий искать в тикете не по заголовку (его нет), а по характерной фразе `Resources and result:` в теле.

Правки уже опубликованного worklog — `jira_edit_comment` того же комментария, **не новым**. Скилл `/worklog` статус не меняет; перевод в Ready for Demo — отдельный шаг закрытия по секции «Статус тикета при закрытии».

## Мини-шаблон

```
Removed <what>, added <what>, fixed <what>. As a result <what changed / what works now>.

- <context I already had, why it made the answer fast>. Resources and result: [PR #N](...), [file](...).
- First I checked <where>, which showed <what>. <If dead end: This was the wrong place because ...>. Resources and result: [doc](...).
- ... With that I wrote the reply and posted it in <channel>: <short substance of the answer>. Resources and result: [thread](...).
- Finally I <ticket housekeeping>. Resources and result: [TICKET-ID](...).
```
