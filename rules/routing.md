# Маршрутизация задач: AIDD vs прямая сессия

## Главный принцип (критично)

Claude **НИКОГДА не выбирает режим сам на 100%**. На каждую новую задачу Claude:

1. Даёт рекомендацию с кратким обоснованием.
2. Задаёт вопрос пользователю, какой режим запускать.
3. **СТОП** — ждёт решения.

Действие начинается **только после ответа пользователя**. Пользователь либо принимает рекомендацию, либо выбирает другой режим — Claude следует решению без спора.

## Когда протокол срабатывает

Срабатывает:
- На каждую новую постановку задачи (фича / баг / улучшение / операция), включая первую в сессии.

НЕ срабатывает:
- Продолжение уже запущенного режима / тикета в той же сессии.
- Чистые вопросы и исследование без изменения кода — просто отвечаем.
- Тривиальные уточнения к текущей работе.
- Явный вызов скилла этапа (`/idea`, `/plan`, `/tasks`, `/implement`, `/review`, `/qa`, `/docs-update`, `/validate`, `/feature-development`) — это уже решение пользователя о режиме, маршрутизация не требуется.

## Rubric классификации

Три вопроса. **≥2 «да» → рекомендуй AIDD**, иначе → прямая сессия.

| # | Вопрос | Если «нет/да» |
|---|--------|---------------|
| 1 | Знаю ли точно, что и как делать? | Нет → +AIDD |
| 2 | Затронет >2–3 файлов или staging/production? | Да → +AIDD |
| 3 | Будет формальное ревью / аудит / ServiceNow CR? | Да → +AIDD |

Дополнительный контекст: активный `docs/.active_ticket` → возможно продолжение AIDD (учесть при рекомендации).

## Сильные сигналы «прямая сессия»

- Вопрос / исследование без правок.
- Тривиальное изменение: 1 файл, опечатка, bump тега TF-модуля (`?ref=`), одно поле в `image.json`.
- Точечный багфикс с ясной причиной.
- SRE-операция: `kubectl` / `gcloud describe` / `list` / `verify`.
- Механика по готовому образцу: скопировать `.tf` агента, сменить `repo_name`.

## Сильные сигналы «AIDD»

- Новая фича с объёмом (>2–3 файлов / компонентов).
- Размытые требования.
- Staging / production → нужен ServiceNow CR и аудит-trail.
- Незнакомая область (сначала research).
- Работа на несколько сессий.

## Формат рекомендации

Выдавать на каждую задачу:

```
🔀 Рекомендация: <прямая сессия | AIDD>
   <2–3 фактора из rubric, через ·>
   Какой режим запускаем? (прямая / AIDD / уточнить)
— жду твоего решения
```

После формата — **СТОП**.

## После ответа пользователя

- Выбор «прямая» → обычный режим без ограничений AIDD.
- Выбор «AIDD» → читай `~/.claude/workflow.md`, Этап 1 (или продолжение существующего тикета).
- Пользователь выбрал режим, отличный от рекомендации → следуй его решению.

## Закрытие задачи (оба режима)

Любая задача с тикетом, независимо от режима (прямая сессия или AIDD), при закрытии завершается так:

1. Актуализировать описание тикета по шаблону `ticket-description.md` (As a / We want / So that / Description / Given-When-Then).
2. Вызвать `/worklog <ticket>` (или выполнить его алгоритм по `ticket-worklog.md`).
3. Подготовить комментарий-резюме `Summary of work done:` (`ticket-worklog.md`, секция «Комментарий-резюме»).
4. Показать черновики (описание, worklog, резюме) — **СТОП**.
5. После подтверждения — обновить описание, опубликовать worklog, затем резюме самым последним комментарием.
6. Перевести тикет в **Ready for Demo** (никогда в `Done`) — через агента `general-purpose`; порядок строго: описание → worklog → резюме → статус. Детали — `ticket-worklog.md`, секция «Статус тикета при закрытии».

**Без worklog задача не считается закрытой.**

**Done не используем: в Done переводит пользователь после демо.**

- В AIDD — Этап 9 `~/.claude/workflow.md`.
- В прямой сессии — обязательный последний шаг после отправки ответа / merge PR.

## Груминг тикетов из Slack

Тикеты с заголовком `New Slack Ticket from <EMAIL>` приводятся в человеческий вид **всегда** — заголовок с краткой сутью, описание по шаблону `ticket-description.md` после сохранённых реквизитов (email автора + Slack-ссылка).

Момент — когда суть задачи ясна: в AIDD после PRD (Этап 1) и плана (Этап 3), в прямой сессии — в эквивалентный момент. Не откладывать до закрытия тикета. Детали — `ticket-grooming.md`.

## Смотри также

- `workflow.md` — протокол AIDD
- `ticket-description.md` — шаблон описания тикета
- `ticket-grooming.md` — груминг Slack-тикетов, когда суть задачи ясна
- `ticket-worklog.md` — worklog и комментарий-резюме при закрытии задачи
- `CLAUDE.md` — точка входа
