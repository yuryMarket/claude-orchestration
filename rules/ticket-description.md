# Описание (description) Jira-тикета

## Назначение

Единый стандарт тела тикета: по описанию сразу видно, кто, что и зачем делает и как проверить результат. Формат утверждён пользователем на `COR1-637`. Эталоны: описания `COR1-637` и `COR1-610`.

## Когда применять

- При создании тикета и при груминге, когда суть задачи ясна (AIDD — после PRD и плана; прямая сессия — эквивалентный момент).
- При закрытии задачи — актуализировать описание по факту выполненной работы, до worklog (см. `ticket-worklog.md`).
- По запросу «переделай задачу в формат» — см. `ticket-worklog.md`, секция «Приведение существующего тикета к формату».

## Шаблон

Каждая жирная метка — отдельный абзац:

```
**As a** <роль, обычно SRE Engineer>

**We want:** <что нужно сделать>

**So that:** <зачем, ожидаемый эффект>

**Description:** <один абзац: контекст, причина, что делаем по шагам, что вне scope>

**Acceptance Criteria:**

**Given:** <исходное состояние — подготовленная работа>

**When:** <действие или событие, которое запускает проверку>

**Then:** <наблюдаемый проверяемый результат, ответ да/нет>
```

## Правила содержания

- Без нумерованных списков и без markdown-заголовков (`#`, `##`). Scope и шаги сворачиваются в один абзац `Description`.
- Факты не выдумывать. Сохранять все ключевые детали исходного описания: ID, версии, теги, имена ресурсов, ссылки.
- `Then` — проверяемый результат: по нему можно однозначно ответить «да» или «нет».
- Резюме проделанной работы в описание **не** добавлять — оно идёт отдельным комментарием `Summary of work done:` (см. `ticket-worklog.md`).
- Slack-тикеты (`ticket-grooming.md`): реквизиты `Description` / email автора / Slack-ссылка остаются в самом начале, шаблон идёт после них.
- Ключи тикетов в описании — только явной ссылкой: `[COR1-N](https://thd.atlassian.net/browse/COR1-N)`. Rovo не автолинкует голый ключ.

## Язык

- Язык тикета (для THD Jira — английский). Общение с пользователем в чате — русский.
- Простой английский B1, максимум B2: короткие предложения, простые слова.
- Технические термины и идентификаторы — как есть, в backticks.
- Без оценок и ремарок о важности, без упоминаний Claude / ИИ / агентов.

## Как выполнять

1. Перед правкой сохранить исходное описание и комментарии тикета в `docs/reports/<ticket>-description-original.md` (в проекте) или `~/docs/reports/` (вне проекта) — правка должна быть обратимой.
2. Подготовить черновик описания → показать пользователю → **СТОП**.
3. После подтверждения — запись через агента `general-purpose`, **всегда** Rovo: `mcp__claude_ai_Atlassian_Rovo__editJiraIssue`, формат markdown. Заголовок (summary) при необходимости меняется тем же вызовом. Оркестратор `mcp__*` не вызывает — см. `mcp-isolation.md`.
   - **Не** использовать `mcp__atlassian__jira_update_issue` для описания: mcp-atlassian портит Markdown при конвертации в ADF (email с двумя `_` становится курсивом, выпадает `+`, ломаются фигурные скобки в inline-code). Rovo сохраняет ровно текст файла (проверено на `COR1-659`, 2026-10-30).
4. Обратное чтение — тоже через Rovo: `mcp__claude_ai_Atlassian_Rovo__getJiraIssue` (ридер `mcp__atlassian__jira_get_issue` показывает текст с искажениями). Проверить: метки — отдельные абзацы, bold отрендерился, реквизиты Slack на месте, ключи тикетов — ссылки.

Комментарии (worklog, резюме) остаются на mcp-atlassian: `jira_add_comment` / `jira_edit_comment` — см. `ticket-worklog.md`.
