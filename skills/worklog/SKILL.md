# Оформление тикета при закрытии

Готовишь три артефакта тикета — описание, worklog, комментарий-резюме — и публикуешь их в Jira от имени пользователя.

**Источники истины по формату — прочитай перед написанием текста и следуй дословно:**
- `~/.claude/rules/ticket-worklog.md` — worklog, секции «Комментарий-резюме» и «Приведение существующего тикета к формату»
- `~/.claude/rules/ticket-description.md` — шаблон описания тикета
- `~/.claude/rules/ticket-grooming.md` — реквизиты Slack-тикетов

Эталон: COR1-637 (описание, worklog-комментарий 4449724, резюме 4497131); шаблон описания — COR1-610.

Ключевые инварианты (полный свод — в правилах):
- **Описание**: абзацы `**As a**` / `**We want:**` / `**So that:**` / `**Description:**` (один абзац: контекст, причина, шаги, вне scope) / `**Acceptance Criteria:**` / `**Given:**` / `**When:**` / `**Then:**`; без списков и заголовков; у Slack-тикетов реквизиты (Description / email / Slack-ссылка) в начале; резюме в описание не кладётся
- **Worklog**: без заголовков; резюме результата → bullet-шаги (не нумерованные), каждый заканчивается `Resources and result:` + проверенные ссылки; первое лицо; английский B1 (максимум B2): короткие предложения, простые слова, термины и идентификаторы как есть
- **Резюме**: отдельный, самый последний комментарий после worklog; первая строка `Summary of work done:`, затем нумерованный список однострочных пунктов — конкретное действие со ссылкой и тем, что оно дало (`[PR #N](url): what it did`, сборка, деплой, endpoint, проверка); worklog не заменяет
- **Тулы публикации**: описание (и заголовок) — только Rovo `mcp__claude_ai_Atlassian_Rovo__editJiraIssue` (markdown, дословно), чтение описания — `mcp__claude_ai_Atlassian_Rovo__getJiraIssue`; `mcp__atlassian__jira_update_issue` для описания не использовать — портит Markdown (`_` в email → курсив, теряется `+`, ломаются `{}`), а `jira_get_issue` искажает показ описания (COR1-659). Комментарии — `mcp__atlassian__jira_add_comment` / `jira_edit_comment`
- Во всех текстах — без упоминания ИИ, агентов, сессий, инструментов; язык тикета (THD Jira — английский)

## Входные данные

- `$ARGUMENTS` — один или несколько ticket ID
- Если не передан — резолюция активного тикета:
  1. Primary: session_id из строки контекста `AIDD session_id: <S>` → `~/.claude/sessions/aidd/<S>.json`, поле `ticket`
  2. Fallback (legacy): `docs/.active_ticket`
  3. Если пусто — спроси пользователя
- Режим определяется так: **Закрытие** — задача только что решена; **Приведение к формату** — пользователь прислал уже закрытые тикеты («переделай в формат») или `/worklog` вызван постфактум и в тикете уже есть worklog

Пути артефактов: в проекте — `docs/reports/`, вне проекта — `~/docs/reports/` (`~/.claude/rules/docs-storage.md`). Несколько тикетов — алгоритм выполняется по каждому отдельно.

## Алгоритм

1. Определи тикет и режим (см. «Входные данные»).
2. Прочитай три rules-файла из списка выше.
3. Получи тикет: `Agent(quick-lookup)` с промптом
   `Получи Jira тикет <ID>. Верни: title, status, description дословно, все комментарии дословно с id, авторами и датами, remote links/PR, историю статусов.`
4. Бэкап исходника: запиши описание и все комментарии дословно (с id и авторами) в `docs/reports/<ticket>-description-original.md`. Если файл уже есть — не перезаписывать.
5. Найди существующие комментарии пользователя: worklog — по фразе `Resources and result:`, резюме — по первой строке `Summary of work done:`. Запомни их id.
6. Собери факты — ничего не выдумывать:
   - **Транскрипты**: `grep -l` по `~/.claude/projects/<slug cwd>/*.jsonl` (slug = абсолютный путь cwd с заменой `/` на `-`) по ID тикета, именам ресурсов, автору запроса; дамп — Write скрипта в scratchpad → `python3 <абсолютный путь>`
   - **Локальные артефакты**: `docs/prd|research|plan|tasklist|reports|investigations/<ticket>*`, `~/docs/quick-lookup/`, `~/infra-operator-logs/`
   - **GitHub**: `gh pr view <N> --json url,state,mergedAt,title`; `gh api repos/<org>/<repo>/contents/<path> --jq .html_url` — каждая ссылка проверена, файлы ведут на `blob/main/...`
   - **Состояние систем** (при необходимости): read-only `bq` / `gcloud` / `kubectl`
   - В режиме «Приведение к формату», если worklog уже есть, — его факты и ссылки — основной источник; сбор по транскриптам только для пробелов
7. Напиши три черновика (существующие файлы обновлять, копий не создавать):
   - `docs/reports/<ticket>-description.md` — описание по `ticket-description.md`, все факты исходного описания сохранены; ключи тикетов — только явной ссылкой `[COR1-N](https://thd.atlassian.net/browse/COR1-N)` (Rovo не автолинкует ключи)
   - `docs/reports/<ticket>-worklog.md` — worklog на B1; если worklog уже опубликован — переписать его язык на B1, факты, шаги и ссылки сохранить
   - `docs/reports/<ticket>-summary.md` — резюме `Summary of work done:`
8. **СТОП — черновики на подтверждение.** Покажи три текста (или пути + сводку ≤10 строк: число шагов worklog, пунктов резюме, ссылок, что изменилось в описании). Правки вносятся в те же файлы. Без явного «ок» дальше не идти.
9. Публикация (только после подтверждения) — один `Agent(general-purpose)` с промптом:
   ```
   Тикет <ID>. Выполни строго по порядку, Markdown передавать как есть (не переводить в wiki-разметку).
   Статус, assignee и другие поля не менять. Чужие комментарии не трогать. Один вызов тула = одно действие.
   1. mcp__claude_ai_Atlassian_Rovo__editJiraIssue: description = содержимое <абс. путь description.md>
      дословно, формат markdown. [Только для груминга Slack-тикета: тем же вызовом summary = "<новый заголовок>".]
      mcp__atlassian__jira_update_issue для описания НЕ использовать.
   2. Worklog = содержимое <абс. путь worklog.md>: если задан id <WORKLOG_ID> — mcp__atlassian__jira_edit_comment
      этого комментария, иначе mcp__atlassian__jira_add_comment.
   3. Резюме = содержимое <абс. путь summary.md>: если задан id <SUMMARY_ID> и он последний — jira_edit_comment;
      иначе jira_add_comment (резюме должно быть самым последним комментарием).
   4. Обратное чтение. Описание (и заголовок) — через mcp__claude_ai_Atlassian_Rovo__getJiraIssue: текст совпадает
      с файлом, абзацы As a..Then не слились, реквизиты Slack на месте, ссылки на тикеты кликабельны.
      Комментарии — через mcp__atlassian__jira_get_issue: worklog начинается с резюме, bullet-список отрендерился,
      у каждого пункта есть "Resources and result:"; резюме — последний комментарий, нумерация 1..N подряд
      (не 1,1,1); URL не разорваны.
   Верни id/URL обоих комментариев и результат проверки, ≤8 строк.
   ```
10. Итог пользователю: URL комментариев `https://thd.atlassian.net/browse/<ID>?focusedCommentId=<id>`, пути к четырём файлам, замечания рендера, явно — статус тикета не менялся.

## Запреты

- Не менять статус тикета — перевод в Ready for Demo отдельный шаг закрытия (`ticket-worklog.md`, «Статус тикета при закрытии»)
- Не публиковать в Jira без подтверждения пользователя и без бэкапа исходника
- Не вызывать `mcp__*` напрямую — только через `Agent` (`~/.claude/rules/mcp-isolation.md`)
- Не писать описание через `mcp__atlassian__jira_update_issue` и не проверять его через `jira_get_issue` — только Rovo
- Не создавать второй worklog- или резюме-комментарий в тикете — править существующий
- Не редактировать и не удалять чужие комментарии
- Не терять при переписывании факты, ссылки, реквизиты Slack
- Нумерация — только в резюме; в worklog и описании нумерованных списков нет
- Не использовать URL со спецсимволами `!`; не выдумывать шаги, ссылки и результаты
